# `crates/core` — `jellysink-core`

- `config/` — `paths.rs` (`Paths`: the config dir and every file in it, plus the cache dir jellytui's covers live in), `settings.rs` (`Config` — config.toml — and `Field`, the exhaustive list of user-facing keys), `mpv_args.rs` (`MpvArgs`, mpv_args.conf, re-read on every mpv spawn), `credentials.rs` (`Credentials`, cred.json, mode 0600), `server.rs` (`normalize_server_url` — bare host → `http://host`, no port is ever invented — and `device_name`). `atomic_write` lives in `mod.rs`, where all three writers reach it — and jellytui's cover cache, which needs the same tmp-and-rename for the same reason.
- `logging.rs` — `init_tracing`; the filter is `RUST_LOG` or `info`, and it is an `EnvFilter`, so the full `target[span{field}]=level` syntax works — `Targets` would drop the `regex` dependency and is deliberately not used. There is no `log_level` config key: the environment variable every Rust user already knows is the whole interface. `log_filter` is `pub` because `jellytui` builds its own subscriber (`crates/jellytui/src/logs.rs`); `init_tracing` itself stays daemon-only, because it writes to stdout and would paint over the alternate screen.
- `cast.rs` — `CastEvent`: the Jellyfin remote-control commands (PlayNow/Pause/Seek/…) parsed from WebSocket messages. Parsing only. Shared because `jellysink` receives these and `jellytui` sends them.
- `jellyfin/` — server API: `auth.rs` (login, `Api` client, cached auth header, `AuthExpired`, and the `get`/`post`/`post_json`/`get_json` transport helpers), `browse.rs` (the listing endpoints — `user_views`, `items` + the `ItemQuery` builder, `seasons`, `episodes`/`episodes_all`, `next_up`, `resume`, `get_item`), `remote.rs` (driving *another* session: `session_for_device` and `play_now`, which is all jellytui sends — playback control is mpv's, see `specs/tui.md`; note `session.rs` is the WebSocket and `remote.rs` is remote control, they are not the same thing), `model.rs` (the typed `Item`/`UserData`/`Session`/`PlayState` DTOs the frontend renders; the playback path still works in `Value` because it forwards rather than displays), `session.rs` (WebSocket URL + message parsing), `url.rs` (stream and image URLs, and `redact_api_key`), `encode.rs` (`encode_query_value`).
- `status.rs` — `PlayerStatus` / `NowPlaying`, the wire format of `jellysink status` and of jellytui's once-a-second footer poll. Serialized by the daemon, deserialized by both clients, so it belongs to neither.
- `update.rs` — the one GitHub-release self-updater, parameterised by binary name so either binary can be checked, installed in place, or installed beside the running one. `install_both` is the whole `update` subcommand — both binaries and then the daemon's restart — so `jellysink update` and `jellytui update` are one flow. The `println!`s here are that subcommand's output; `update.rs` is the only file in core that prints. See `specs/tui.md`.
- `instance.rs` — the single-instance lock and the `stop.sock` client: `stop`, `restart` (any update path) and `status`. One attempt each; a socket with nothing behind it is "not running" and a listener that does not answer within `STATUS_REPLY_TIMEOUT` (under the 1 Hz poll interval) is "not responding" (`specs/session.md`). The listener that answers them is the daemon's.
- `ticks.rs` — Jellyfin position ticks (100 ns units) ↔ seconds, plus `format_hms` for anything that prints a position. Nothing to do with media.
- `json.rs` — the lenient number coercions the two wire formats need: Jellyfin quotes some tick fields and mpv answers a property with whichever JSON number shape fits. `coerce_f64` is `pub` because `mpv/command.rs` reads `time-pos` through it; the strict property readers in `mpv/ipc.rs` are the deliberate opposite and stay there.
- `error.rs` — `UsageError` / `usage_err`.
