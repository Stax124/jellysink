# `crates/jellytui` — the terminal frontend

A *remote*, not a second player: it never builds a `Runtime`, never spawns mpv and never takes `instance.lock`, so it runs happily alongside the daemon. It browses Jellyfin directly, and talks to the daemon only over `control.sock`: Enter on a row sends a `play_now` command, and the status and events the daemon pushes back drive the footer and settle the play as started, failed, cancelled or refused (`specs/tui.md`).

- `cli.rs` — `jellytui update`, the only subcommand, over core's `install_both`; `update_and_restart` is the same flow for the `u` key, plus the `exec` that brings the TUI back. See `specs/tui.md` for why replacing a running binary is safe.
- `app/` — state and the loop: `mod.rs` (`App`, the `select!` loop, key handling, and `Exit` — why the loop ended), `update.rs` (the startup check and the `u` key, which ends the loop so the install gets the normal screen back), `msg.rs` (what the spawned request tasks and the daemon connection send back; one task per request so HTTP never blocks a keystroke), `browse.rs` (where the cursor is, and the browse stack), `request.rs` (every outbound browse call), `player.rs` (the one reconnecting `control.sock` connection, the play shown as starting until an event with its own origin settles it, and the `play_now` a keypress turns into), `logs.rs` (where the log pane is scrolled to).
- `view/` — drawing: `mod.rs` (terminal setup through `ratatui::try_init`, whose panic hook restores the terminal; the shared layout; and the chrome — header, footer, hints), `body.rs` (the three screen bodies), `grid.rs` (the tile wall), `synopsis.rs` (the band under every grid but Libraries), `rail.rs` (the detail rail beside a list), `overview.rs` (an overview's HTML as styled lines), `playing.rs` (the `3 Playing` screen), `logs.rs` (the log pane).
- `nav.rs` — the browse stack and `Rows`, the items-plus-cursor every screen moves through, plus `mode` — which view a level's rows get.
- `keys.rs` — key → `Intent`, a pure mapping so bindings are testable; `Left`/`Right` stay unresolved here because what they mean depends on the focused view.
- `cover/` — `mod.rs` (the `Picker`, the bounded in-memory cache of encoded protocols, and the shared cell-vs-pixel geometry), `disk.rs` (the covers kept between sessions: the server's bytes rather than a protocol, keyed on the request's own pixel bucket, LRU by mtime under `cover_cache_mb`). Not under `view/`: it fetches and caches, and lays nothing out — `Covers::draw` only places a cover that has arrived. See `specs/tui.md`.
- `logs.rs` — the tracing subscriber jellytui installs and the ring buffer behind the `L` screen. Its only sink is memory: a `fmt` layer would write to the alternate screen. It captures `jellytui` and `jellysink-core`, never the daemon — that is another process. See `specs/tui.md`.
